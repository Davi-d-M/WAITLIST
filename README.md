# Midnight Society KE

This folder is an independently deployable Next.js site. It uses the same Supabase project as Online Bar Admin, so waitlist signups, invite credits, souvenir requests and editable content stay connected without exposing the service-role key in browser code.

## Deploy

1. Apply `supabase/WAITLIST_SITE_MIGRATION.sql`, `supabase/WAITLIST_FIT_STUDIO_MIGRATION.sql`, then `supabase/WAITLIST_FIT_STUDIO_MARKETPLACE_MIGRATION.sql` to the shared Supabase project used by both this site and Online Bar Admin—not a separate/local database. The first migration creates/extends the shared waitlist, private referral-token ledger, souvenir catalog and request tables, atomic reward-claim function, editable campaign content, and public-read-only image/audio buckets. The Fit Studio migration adds private member profiles, requested services, consent history, provider coordination, Admin audit and server-only atomic operations. The marketplace migration adds priced/photo listings, member booking requests and the public listing image bucket. The site migration also backfills verified auth-user links to existing waitlist signups by normalized email and installs the trigger that keeps future signup/email changes linked for Online Bar order attribution. To enable or update member recovery on an existing deployment, run `supabase/WAITLIST_MEMBER_RECOVERY_MIGRATION.sql` in that same project.
   If the site migration was already applied before anonymous music analytics were added, also run `supabase/WAITLIST_MUSIC_ANALYTICS_MIGRATION.sql` in the same project's Supabase SQL Editor. This focused, repeatable patch updates only the analytics event table and its reporting function; it avoids reapplying unrelated waitlist, referral, and member-session schema. Without it, the public picker still works, but analytics event writes can fail and Admin genre counts will not populate.
2. For first-party session replay shared across all three sites, also apply Online Bar's `supabase/SESSION_REPLAYS_MIGRATION.sql` once to the same Supabase project. Recordings require explicit visitor consent and are played inside Online Bar Admin. No PostHog account or additional environment variables are needed.
3. Create a separate hosting project with this folder as its root directory.
4. In the hosting project's private Production environment, set `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to values from the same Supabase project as Online Bar Admin. Never prefix the service-role key with `NEXT_PUBLIC_` or expose it to the browser. Redeploy after setting environment variables.
5. Optionally set `WAITLIST_LAUNCH_AREAS` to comma-separated area names. If unset, the site reads published `settings.logistics.dispatch_zones` from the shared database.
6. The customer-facing **Shop Halloween** page is served at `/halloween` by this Waitlist app. It fetches published products, categories and the published Market campaign from the public Halloween catalog API at `https://halloween-kohl-tau.vercel.app` by default; optionally set `NEXT_PUBLIC_MIDNIGHT_MARKET_URL` to override that origin. Product details, seller applications and merchant operations remain in the Halloween app. Merchant accounts, listings, approval controls and storefront publishing use the shared marketplace database, so only published listings from approved merchants are displayed. The Online Bar **Market Operations** admin and the Halloween merchant studio must use the same Supabase project and the same `NEXT_PUBLIC_SUPABASE_URL` / server-only `SUPABASE_SERVICE_ROLE_KEY` values for product approval, publishing and inventory to flow through the Halloween catalog API to this shop. Apply `supabase/MIDNIGHT_MARKET_STOREFRONT_CONTROLS_MIGRATION.sql` from the Halloween repository to that shared Supabase project before editing or publishing shop copy/countdown in Market Operations. Verify the catalog host is the intended Halloween deployment; the Waitlist page intentionally reads its public API and does not hold database credentials. The public `/api/fit-studio-offerings` endpoint exposes only explicitly published Fit Studio listings (never member data or drafts) to the Halloween app, which reads them as the single source of truth. Product order requests are not online payment: the boutique confirms availability and arranges payment and delivery directly.
   The Waitlist costume page also includes the Online Bar Halloween storefront experience: theme filters and search, size guidance, local photo-color preview, illustrative costume preview, and a browser-local preview bag. The bundled costume designs are explicitly marked as previews—not verified inventory—and cannot be purchased. Live merchant products link to the Halloween marketplace product page for its current availability and order/interest flow. A campaign published in Online Bar Market Operations is displayed on the Waitlist shop through the same catalog response. Photos used in the try-on preview stay in the visitor's browser and are not uploaded. If the catalog API is unavailable, the preview shop remains visible and reports the connection issue.
7. The Admin application resides in the separate Online Bar repository; it is not part of this standalone WAITLIST repository. In Online Bar Admin, open **Early Access Waitlist → Standalone site content** to edit the Midnight Society identity, choose the cream/red/green or classic yellow palette, reveal phase, announcement, experience cards, event copy, confirmed registration URL, launch date and hero image. Choose the palette and click **Publish copy** to apply it; the public site uses the saved palette on its next load or refresh. The same panel manages the age-group/genre music. Referral credit is fixed at 3 tokens per joined referral and is not controlled by the legacy configurable token field. Use **Waitlist phone widget & souvenirs** to add prize descriptions, token costs and images; review member redemption requests there. Admin verifies uploaded music against the live waitlist site's `/api/content` response; if it is saved but not visible there, confirm both deployments use the same Supabase project. Set `WAITLIST_PUBLIC_URL` in the Online Bar Admin environment only if the public waitlist uses a different origin from `https://theewaitlist.vercel.app`.

The standalone application lives in this repository. It publishes **Midnight Society KE**, an experience brand powered by ONLINE BAR, and writes member signups, selected experience paths, referral credits, Fit Studio profiles and souvenir requests to the shared Supabase project; Online Bar Admin reads those same records. The optional Fit Studio questionnaire is linked to the member's existing token-protected waitlist pass and can be skipped without changing their signup. Fit Studio captures outfit theme, readiness, requested help, budget, group plan and separately opted-in contact channels. Admin → Early Access Waitlist in the Online Bar repository is the sole Admin surface for campaign and Fit Studio controls, including uploadable priced/photo offers and member booking requests. Members see published offers matching their saved help categories and can request a booking; requests are not confirmed reservations or payments. Keep both deployments on the same Supabase project and apply all three migrations before launch. Offers appear in members' Fit Studio page when they return; public messages do not send email, SMS or WhatsApp. A registration URL records no ticket purchases. Actual conversion reporting requires the selected ticketing provider's integration.

Waitlist music starts at low volume and fades up gradually after the visitor confirms their age and enters the site. Published page content is fetched without CDN caching so newly assigned music tracks appear immediately. Signup requires an experience choice (wine tastings and gifts, hosted adventures, or the Soul Fest ticket draw); each choice is saved to `market_waitlist.reward_path` for the Admin signup list and experience summaries.

## Invites, tokens and souvenirs

Each member receives a short link in the form `/invite/OB-XXXXXXXX`. Every new signup earns a fixed 3-token credit for each eligible referrer in its invite ancestry: the direct inviter and every earlier inviter above them, with no generation limit. The credit ledger records one credit per referrer/invitee pair and stores its generation. The migration safely backfills ancestor credits for existing referral chains while preserving prior direct credits and souvenir balances. Self-referrals and repeat-email credits remain blocked, and returning signups do not create extra referral credits. The member dashboard and installable Android widget show cumulative downline referrals, generation-by-generation totals, and token balances.

Members can open the link shown after signup to see invited friends who joined, tokens earned/available, the launch countdown, published souvenirs and request history. On the same browser and device, the private member session restores the saved signup details and shows a return-to-dashboard link. If they switch devices or clear browser data, they can choose **Already joined?** and recover their existing page using the name from signup and the last three digits of their signup phone number; this creates a new private session without making another signup. Recovery is rate-limited, requires a phone number on the original signup, and only succeeds when the name and phone suffix match exactly one waitlist entry. Name capitalization, spaces and punctuation are ignored. Members who joined without a phone number or cannot get a unique match should contact support. The original token remains stored only in browser local storage. Requesting a souvenir atomically reserves its token cost. Admin approval fulfils the request; rejection releases those tokens.

The `/widget` dashboard is an installable PWA/home-screen app shortcut. After signup, the success screen prompts members to open their personal dashboard and add it to their phone; the dashboard provides the browser's install prompt where supported and platform-specific fallback instructions. The shortcut opens the live countdown and referral totals. Browser-hosted sites cannot provide a live, interactive Android/iOS operating-system widget; that requires a native app/widget integration. On iPhone, use Safari's **Share → Add to Home Screen**.

The site records anonymous page opens per browser tab session, selected adult age ranges, music-style picks, and assigned-song starts/listens reaching 80% so Admin can compare interest and track engagement by age group and genre. Visitors choose from visible music-style buttons at the age gate; a style remains selectable even before a sample track is uploaded, and an available matching track plays. The Admin summary counts unique anonymous browser sessions selecting each style (a session may select more than one while exploring). These events are not joined to signup names, email addresses, or locations. The Admin area's signup heat map uses only the city and area members voluntarily provide when joining; it does not infer the location of all visitors from their IP addresses. Re-apply this repository's migration to update the analytics event constraint and Admin summary function.

Android customers can install the separate native home-screen countdown widget in `android-widget`. Build it with `.\gradlew.bat -p android-widget :app:assembleDebug -PwaitlistSiteUrl=https://<your-deployed-waitlist-origin>`. The site URL must be the deployed standalone waitlist HTTPS origin. When a customer joins through the Android app, their private member dashboard token connects the widget to real joined-friend and token balances. Do not publish or share member tokens.

The standalone site is intended for adults of legal drinking age. Uploaded music must be owned or licensed for use. Souvenir redemptions are requests subject to prize availability and Admin confirmation.
